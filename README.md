# rodin-super-repartition

Development-only physical `super` repartition for **POCO X7 Pro / Redmi Turbo 4 (`rodin`)**.

It changes the phone from the factory **11 GiB physical `super`** partition to **20 GiB**, taking exactly **9 GiB from `userdata`**.

The point is ROM/OEM-port development: large temporary `super.img` builds can be flashed without constantly deleting apps or shrinking logical partitions.

**This is not intended as a requirement for normal ROM users.** Once a ROM is finished, it should still be repacked and tested against the stock 11 GiB layout whenever possible so users do not lose 9 GiB of internal storage.

## Verified result

```text
Factory:
super    = 11,811,160,064 bytes = 11 GiB
userdata = 250,170,277,888 bytes

Development:
super    = 21,474,836,480 bytes = 20 GiB
userdata = 240,506,601,472 bytes
```

The physical repartition, moved-partition readback, GPT CRCs, recovery reboot, new `/data` format, and fastboot acceptance of a sparse `super.img` were validated on-device.

See [`docs/TESTED.md`](docs/TESTED.md) for the exact validation record.

## Read this first

This changes the physical UFS GPT.

A wrong device layout, bad offset, interrupted write, or GPT generated for a different phone can make the device unbootable.

The project therefore follows four rules:

1. **No universal prebuilt GPT binary.** GPT structures are generated from *your own* original GPT backup.
2. **Exact geometry validation.** The generator refuses a stock layout that does not match the validated rodin geometry.
3. **Move and verify before switching GPT.** Every relocated partition is read back byte-for-byte first.
4. **Keep the reverse path.** The exact original stock GPT structures are extracted to `out/stock/` so the 11 GiB layout can be restored later.

Have a proven low-level recovery/unbrick method for your device before proceeding.

---

## What changes physically?

Stock:

```text
[ super 11G ][ ffu ... blackbox ][ userdata ][ flashinfo ]
```

Development:

```text
[ super 20G ][ ffu ... blackbox ][ userdata ][ flashinfo ]
```

`ffu` through `blackbox` are shifted forward exactly **9 GiB**.

`super` keeps the same start LBA. `flashinfo` does not move. `userdata` keeps its original end, but its start moves forward by 9 GiB, so **Format Data is mandatory**.

Exact LBAs are in [`docs/TECHNICAL.md`](docs/TECHNICAL.md).

# Requirements

- POCO X7 Pro / Redmi Turbo 4 (`rodin`)
- exact storage geometry documented in this repository
- unlocked bootloader
- custom recovery with root ADB; OrangeFox was used for validation
- Linux or WSL host
- `adb`, `fastboot`, Python 3
- enough host storage for backups
- a known-good device recovery/unbrick path

Do not continue if preflight geometry differs.

# 1. Preflight

On the stock 11 GiB layout:

```bash
scripts/00-preflight.sh
```

Expected core sizes:

```text
/dev/block/sdc                 264484421632
/dev/block/by-name/super        11811160064
/dev/block/by-name/userdata    250170277888
```

Also compare the partition starts/sizes with `profiles/rodin.json`.

---

# 2. Back up everything we move

```bash
scripts/01-backup.sh ~/rodin-super-backup
```

It saves:

```text
sdc-first-4MiB.bin
sdc-last-4MiB.bin
ffu.img
mem.img
countrycode_a.img
countrycode_b.img
oops.img
charger.img
rescue.img
blackbox.img
flashinfo.img
SHA256SUMS.txt
```

Copy this backup somewhere safe and off-device before continuing.

Never use another user's GPT backup as your rollback image.

---

# 3. Generate both GPT layouts offline

```bash
scripts/02-generate.sh ~/rodin-super-backup out
```

This creates:

```text
out/
├── dev20g/
│   ├── primary-header.bin
│   ├── primary-entries.bin
│   ├── backup-entries.bin
│   ├── backup-header.bin
│   └── manifest.json
└── stock/
    ├── primary-header.bin
    ├── primary-entries.bin
    ├── backup-entries.bin
    ├── backup-header.bin
    └── manifest.json
```

`dev20g/` is generated by changing only the required first/last LBAs and recalculating GPT CRC32.

`stock/` is extracted from the exact original GPT backup and is the clean reverse path.

The generator is offline-only and never writes a block device.

---

# 4. Boot recovery and unmount `/data`

```bash
adb reboot recovery
```

Then:

```bash
adb shell '
twrp unmount data 2>/dev/null || umount /data 2>/dev/null || true
mount | grep " /data " || echo DATA_UNMOUNTED
'
```

Do not continue unless `/data` is unmounted.

---

# 5. Stage the moved partitions

This is the first destructive step. It writes the future `ffu` → `blackbox` locations into sectors currently belonging to userdata, so the old `/data` filesystem is lost from this point onward.

```bash
scripts/03-stage-moved-partitions.sh \
  ~/rodin-super-backup \
  I_UNDERSTAND_DATA_WILL_BE_LOST
```

Every moved partition is immediately read back and compared byte-for-byte. The script stops on the first mismatch.

**Do not reboot after this step.**

---

# 6. Switch GPT to 20 GiB

```bash
scripts/04-apply-20g-gpt.sh \
  out/dev20g \
  WRITE_20G_GPT
```

The script deliberately writes in this order:

1. push and hash-check generated GPT files
2. backup GPT entry array
3. backup GPT header
4. primary GPT entry array
5. primary GPT header
6. `sync`
7. raw readback + hash verification of all four writes

Then reboot **directly back into recovery**:

```bash
adb reboot recovery
```

---

# 7. Verify the 20 GiB layout

```bash
scripts/05-verify-20g.sh ~/rodin-super-backup
```

The critical values are:

```text
super    : 21474836480
userdata : 240506601472
```

Manual check:

```bash
adb shell '
blockdev --getsize64 /dev/block/by-name/super
blockdev --getsize64 /dev/block/by-name/userdata
'
```

The 20 GiB physical super size is also:

```text
0x500000000
```

`ffu`, `mem`, `countrycode_a`, `countrycode_b`, `oops`, and `charger` are expected to remain exact hash matches after reboot.

`rescue` and `blackbox` were exact matches before the GPT switch, but both can legitimately change after recovery boots; details are in [`docs/TROUBLESHOOTING.md`](docs/TROUBLESHOOTING.md).

---

# 8. Format Data

Because userdata now starts at a different LBA, the old filesystem is invalid.

In OrangeFox:

```text
Wipe
→ Format Data
→ type yes
```

Reboot recovery once afterward and confirm `/data` mounts on the new size.

---

# 9. Flash the development `super.img`

If your `super.img` already contains valid LP metadata for the larger container, no additional LP repartition step is needed.

From bootloader fastboot:

```bash
adb reboot bootloader
fastboot getvar partition-size:super
fastboot flash super super.img
```

For the development layout, `partition-size:super` should represent:

```text
0x500000000
```

Sparse images are fine and may be sent in many chunks.

A warning such as:

```text
Warning: skip copying super image avb footer due to sparse image.
```

is not by itself a failure. The actual send/write operations still need `OKAY`, and the command must finish without `FAILED`.

Then flash any other ROM-specific images your build requires and boot normally.

# Why this should stay a developer tool

The 20 GiB layout is useful while bringing up huge OEM ports, but it costs about 9 GiB of userdata.

Recommended workflow:

```text
Development phone:
20 GiB physical super
→ easier bring-up / debugging / oversized builds

Public ROM:
repack and optimize
→ test on factory 11 GiB physical super
→ users keep their storage
```

So this repo is a development convenience, not something ordinary users should be forced to run for a finished ROM.

# Returning to factory 11 GiB

Full rollback documentation is here:

**[`docs/RESTORE-STOCK.md`](docs/RESTORE-STOCK.md)**

Short version:

```text
20 GiB development layout
        ↓
boot recovery + unmount data/dynamic partitions
        ↓
restore ffu → blackbox at original LBAs
        ↓
restore exact original GPT
        ↓
reboot recovery
        ↓
super = 11 GiB again
        ↓
Format Data
        ↓
flash an 11-GiB-compatible super.img
```

Both the current 20 GiB super contents and `/data` are considered disposable during rollback.

# Safety rules

- Never run this on a different device just because it also uses MediaTek.
- Never assume another firmware revision has identical physical GPT geometry.
- Never write GPT while `/data` is mounted.
- Never reboot between staging the moved partitions and switching GPT.
- Never restore stock GPT before first restoring the moved small partitions to their stock locations.
- Never distribute a GPT generated from one phone as a universal binary.
- Preserve the original backup permanently.
